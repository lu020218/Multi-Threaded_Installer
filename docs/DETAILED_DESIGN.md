# Detailed Design

## Architecture

The system is split into four major areas:

- `src/packager`
  builds installers from an input directory and `packager.yaml`
- `src/installer`
  handles install, repair, uninstall, cleanup, and payload extraction
- `src/gui`
  handles installer and uninstaller UI
- `src/common`
  shared types, metadata, compression helpers, logging, and runtime utilities

## Packager Design

### Flow

1. parse CLI arguments
2. load `packager.yaml` / `packager.yml`
3. validate schema version 2 config
4. scan top-level folders from input directory
5. apply configured destination mapping
6. compress each folder as one standard payload
7. generate metadata
8. write installer and optional external data package

### Configuration Design

Current config model is grouped into 6 top-level blocks:

- `app`
- `package`
- `install`
- `ui`
- `layout`
- `lifecycle`

There is no compatibility layer for old flat config keys.

`ConfigurationLoader` only accepts:
- `schemaVersion: 2`
- YAML files

### Folder Payload Model

Packager no longer produces custom block metadata.

Current payload model:
- one top-level input folder -> one payload
- payload algorithm:
  - `XZ/LZMA2`
  - `ZSTD`
- payload content is the tar-like stream for that folder
- metadata only describes the folder payload and file index

## Metadata Design

Metadata is generated by `MetadataGenerator`.

Important metadata areas:
- application identity
- install defaults
- folder payload mappings
- file index for each payload
- component definitions
- UI component binding
- lifecycle cleanup and registry data

The metadata format no longer contains:
- block index
- block metadata header
- segment overlap install information

## Installer Design

### Launch Flow

The installer and uninstaller have independent binaries and fixed internal flow.
YAML no longer controls install step ordering.

### Install Execution Model

Current install execution path:
- folder-level scheduling
- folder payload read
- standard stream decompression
- tar stream extraction to target path

Current concurrency model:
- folder-level parallelism
- `XZ/LZMA2` payloads may use runtime-gated multi-threaded decoder support
- `ZSTD` uses stream decompression

### Removed Legacy Path

The old install path has been removed from the active code path:
- no block metadata probing
- no block overlap calculation
- no file segment scatter write
- no indexed vs legacy dual extraction path

## GUI Design

GUI configuration comes from installer metadata, not packager YAML at runtime.

Important UI areas:
- welcome page and component selection
- localized desktop shortcut display name
- install progress and completion page
- uninstall flow

## Cleanup and Lifecycle

Lifecycle configuration is grouped under:
- `lifecycle.compatibility`
- `lifecycle.registry`
- `lifecycle.cleanup`

This covers:
- legacy app ids
- legacy desktop shortcut names
- install-time registry writes
- upgrade cleanup
- uninstall cleanup
- post-setup agent configuration

## Validation Rules

Validation is handled by `ConfigurationValidator`.

Key checks:
- `schemaVersion == 2`
- required fields exist
- destination types are valid
- source folders exist
- icon path exists and is `.ico`
- component references and dependency graph are valid
- local installer paths stay relative to install dir
- download installers use secure URL + valid SHA256

## Build and Runtime Dependencies

Pinned third-party dependencies:
- `yaml-cpp`
- `liblzma`
- `zstd`
- `DuiLib`

The project links against prebuilt static libraries from `third_party` where configured.
