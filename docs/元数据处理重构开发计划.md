# 元数据处理重构开发计划

本文档用于规划打包器与安装器元数据处理链路的优化重构。目标是在不破坏现有安装包主流程的前提下，逐步降低元数据协议和业务对象的复杂度，修复已发现的字段丢失问题，并为后续协议演进留出空间。

## 背景

当前元数据链路覆盖以下阶段：

- 打包器从 `PackagerConfiguration` 与 `CompressionResult` 生成 `ExtendedInstallationMetadata`
- 打包器手写二进制序列化 metadata，并追加到 installer 或外置 data package
- 安装器从当前 exe 或外置 data package 中读取 metadata
- 安装器手写二进制反序列化为 `ExtendedInstallationMetadata`
- GUI、安装计划、解压、组件执行、升级清理、卸载清理直接使用同一个大对象

当前设计已经能支撑业务，但复杂度集中在一个大结构和一套顺序敏感的手写二进制协议上，后续新增字段和排查问题的成本偏高。

## 当前问题

### 正确性问题

- `desktopShortcutDefaultName` 与 `desktopShortcutLocalizedNames` 在打包阶段会从配置写入内存对象，但当前序列化和反序列化没有处理这些字段，导致安装器侧快捷方式默认名和本地化名称丢失。
- `validateMetadata()` 主要校验版本、folder 数量和 `payloadMappings` 数量，缺少对扩展 payload、enum、offset/size、必需字段的集中校验。

### 结构复杂度问题

- `ExtendedInstallationMetadata` 同时承载应用标识、安装策略、UI 配置、组件定义、payload 索引、升级清理和卸载清理。
- `payloadMappings` 与 `extendedPayloadMappings` 双存，`targetPath` 与 `target` 双字段表达近似语义，容易出现不一致。
- 基础元数据接口 `generateMetadata()`、`serializeMetadata()`、`parseEmbeddedMetadata()`、`deserializeMetadata()` 仍存在，但主安装链路基本只使用扩展元数据，历史兼容边界不清晰。

### 协议演进问题

- 写入顺序和读取顺序分别散落在 packager 与 installer 代码中，新增字段必须同步修改两端。
- 当前格式没有字段级 tag、section version 或 optional field 机制，任何字段顺序错位都可能导致整包不可读。
- 元数据读取错误日志粒度偏粗，定位具体字段失败成本较高。

## 重构目标

- 修复现有字段丢失问题，确保配置中已定义的业务字段完整 round-trip。
- 明确主协议只有一条正式路径，历史协议要么删除，要么隔离为 legacy。
- 将元数据大对象按业务职责拆分，减少安装器各模块对巨型对象的直接依赖。
- 收敛 folder target 语义，只保留一个安装落点字段。
- 增强运行期 metadata 校验，降低损坏包、不一致包带来的隐性风险。
- 为后续 section 化或 tagged manifest 协议演进建立代码边界。

## 非目标

- 本轮不改变 `packager.yaml` schemaVersion 2 的外部配置形态。
- 本轮不改变安装包 payload 压缩格式。
- 本轮不重写安装器 GUI 或组件安装业务。
- 本轮不要求一次性切换到 JSON、CBOR 或 MessagePack；协议格式升级单独分阶段执行。

## 目标架构

### 逻辑结构

建议引入新的聚合对象 `PackageManifest`，内部按职责拆分：

- `PackageIdentity`：`appName`、`appId`、`appVersion`、`appDirectoryName`、`website`
- `InstallPolicy`：默认安装目录、管理员要求、最低系统版本、mutex、installInfo、killProcesses、默认启动项和桌面图标策略
- `PayloadManifest`：folder 列表、payload offset/size/checksum/algorithm、fileIndex、target
- `ComponentManifest`：组件定义、依赖、source、组件 registry、组件 killProcesses、组件 startup/shortcut 策略
- `UiManifest`：桌面快捷方式默认名和本地化名、组件选择 UI 绑定、链接绑定
- `LifecyclePolicy`：onInstall registry、onUpgrade cleanup、onUninstall cleanup

### 代码边界

建议新增或调整以下文件：

- `include/common/package_manifest.h`：新 manifest 结构定义
- `src/packager/package_manifest_builder.cpp`：从配置和压缩结果构造 manifest
- `include/common/package_manifest_codec.h`：序列化和反序列化接口
- `src/common/package_manifest_codec.cpp`：打包器和安装器共用 codec
- `include/installer/package_manifest_validator.h`：运行期校验接口
- `src/installer/package_manifest_validator.cpp`：运行期校验实现
- `src/installer/legacy_metadata_parser.cpp`：仅在需要兼容旧包时隔离旧协议

## 分阶段计划

### 阶段 1：正确性修复与测试补强

目标：

- 修复已确认字段丢失问题。
- 用测试锁住当前元数据关键字段的 round-trip 行为。

任务：

- 在 `MetadataGenerator::serializeExtendedMetadata()` 中写入 `desktopShortcutDefaultName` 与 `desktopShortcutLocalizedNames`。
- 在 `MetadataParser::deserializeExtendedMetadata()` 中读取上述字段。
- 补充 `schema_regression_tests.cpp`，覆盖桌面快捷方式默认名和本地化名。
- 扩展现有 metadata round-trip 测试，覆盖 UI links、component selection、component local/download uninstall、cleanup rules、payload fileIndex。

验收：

- `SchemaRegressionTests` 通过。
- 打包配置中 `ui.desktopShortcut.defaultName` 和 `ui.desktopShortcut.i18n` 能在安装器 metadata 中读回。

风险：

- 修改二进制字段顺序会影响旧包读取。当前 `IsSupportedMetadataVersion()` 只接受最新 `Constants::VERSION`，应同步递增 metadata version，或确认未发版旧包不需要兼容。

### 阶段 2：运行期校验增强

目标：

- 把 metadata 反序列化后的语义校验集中化，避免损坏或不一致 metadata 进入安装执行。

任务：

- 新增 `ValidateExtendedMetadata(...)` 或 `PackageManifestValidator`。
- 校验 `extendedPayloadMappings.size() == folderCount`。
- 校验 `payloadMappings.size() == folderCount`，如果保留双列表。
- 校验 folder id 唯一、folder target 非空、payload offset/size 不越界。
- 校验 enum 合法值，包括 compression algorithm、registry value type、component source type、uninstall entry scope。
- 校验 component 引用的 folder id 存在，依赖组件存在且无环。
- 校验 download component 的 URL 与 SHA256 基本形态。
- 将 GUI 和静默入口统一改为调用增强校验。

验收：

- 构造损坏 metadata 的单元测试能被拒绝。
- 正常包 metadata 校验通过。
- 入口层不再只依赖 `validateMetadata()` 的基础校验。

风险：

- 运行期校验过严可能拒绝历史包或宽松配置。需要先基于当前 schema regression fixture 明确最小合法字段集。

### 阶段 3：主协议路径收口

目标：

- 明确正式元数据路径，减少历史接口干扰。

任务：

- 全仓库确认是否仍需基础 `InstallationMetadata` 协议。
- 如果不需要，删除或标记废弃以下接口：
  - `MetadataGenerator::generateMetadata`
  - `MetadataGenerator::serializeMetadata`
  - `MetadataParser::parseEmbeddedMetadata`
  - `MetadataParser::deserializeMetadata`
- 如果需要兼容旧包，将旧协议移动到 legacy 文件中，并禁止新主流程直接调用。
- 更新文档，说明正式协议只使用扩展 metadata 或新 `PackageManifest`。

验收：

- 主安装流程只存在一个 metadata 读取入口。
- `rg "parseEmbeddedMetadata|serializeMetadata|generateMetadata|deserializeMetadata"` 不再命中主流程代码。

风险：

- 测试或工具代码可能仍依赖基础协议，需要同步迁移。

### 阶段 4：引入 `PackageManifest` 与 adapter

目标：

- 在不一次性重写安装器所有模块的前提下，引入职责拆分后的 manifest 模型。

任务：

- 新增 `PackageManifest` 及其子结构。
- 新增 `PackageManifestBuilder`，从 `PackagerConfiguration + CompressionResult + FolderInfo` 构造 `PackageManifest`。
- 新增 adapter：`PackageManifest -> ExtendedInstallationMetadata`。
- 打包器先构造 `PackageManifest`，再通过 adapter 生成旧结构并走现有 codec。
- 将阶段 1 和阶段 2 的测试复制到 `PackageManifest` 层。

验收：

- 对外生成的安装包行为不变。
- 新结构能表达当前所有正式业务字段。
- builder 单元测试能独立验证 folder target、组件、UI、cleanup 映射。

风险：

- adapter 期间会短暂存在双模型，需要严格限制旧结构新增字段，避免继续扩大旧模型。

### 阶段 5：安装器模块按职责改用子结构

目标：

- 减少 `ExtendedInstallationMetadata` 或 `PackageManifest` 巨型对象在安装器内部的横向传播。

任务：

- 安装计划构建只接收 `PackageIdentity`、`InstallPolicy`、`ComponentManifest`、`PayloadManifest`、`LifecyclePolicy` 中必要部分。
- 解压执行只接收 `PayloadManifest` 和 component 选择结果。
- GUI 组件绑定只接收 `UiManifest` 和 `ComponentManifest`。
- 升级清理只接收 `LifecyclePolicy.onUpgrade`。
- 卸载 manifest 写入只接收 `LifecyclePolicy.onUninstall` 和安装执行结果。

验收：

- 关键安装模块不再直接依赖完整 manifest 大对象。
- 单元测试可以针对子结构构造输入，不需要填充整套 metadata。

风险：

- 函数签名变化较多，建议逐模块小步迁移。

### 阶段 6：folder target 语义收敛

目标：

- 删除 `targetPath` 与 `target` 双字段语义。

任务：

- 新结构中只保留 `PayloadFolder.target`。
- 打包阶段只从 `layout.folders[].target` 写入 `target`。
- 安装阶段只展开 `target`，支持 `%InstallDir%` 和环境变量。
- adapter 期间保持旧结构字段同步，但标记 `targetPath` 为 legacy。
- 最终删除旧结构时删除 `targetPath` 业务语义。

验收：

- 同一 folder 不再存在两个可能冲突的 target 来源。
- 测试覆盖 `%InstallDir%`、环境变量 target、绝对路径 target。

风险：

- 现有日志或 manifest 可能仍引用 `targetPath` 名称，迁移时需同步改名或保留兼容输出。

### 阶段 7：协议格式 section 化

目标：

- 降低手写顺序协议的演进风险。

建议格式：

```text
[PackageHeader]
[SectionDirectory]
[identity section]
[installPolicy section]
[payloadManifest section]
[componentManifest section]
[uiManifest section]
[lifecyclePolicy section]
[payload blocks]
[DataLocator or package trailer]
```

每个 section 包含：

- `sectionType`
- `sectionVersion`
- `offset`
- `size`
- `checksum`

任务：

- 新增 `PackageManifestCodecV2`，支持 section directory。
- 保留旧 codec 读取能力一个过渡期。
- 将 installer/data package 的 metadata 区块替换为 section 化 manifest。
- `Constants::VERSION` 或协议版本明确递增。

验收：

- 新包使用 section 化 metadata。
- 旧包是否兼容由产品策略明确；若兼容，需要测试双 codec。
- 新增字段时不需要修改无关 section 的读取逻辑。

风险：

- 这是影响面最大的阶段，应在前面业务结构拆分完成后再执行。

## 推荐 PR 顺序

1. 修复 shortcut i18n 字段丢失并补 round-trip 测试。
2. 增强 metadata 运行期校验。
3. 收口或隔离基础 `InstallationMetadata` legacy 路径。
4. 引入 `PackageManifest` 结构和 builder，不改变输出协议。
5. 安装器内部模块按职责改用 manifest 子结构。
6. 收敛 `targetPath`/`target` 双字段。
7. 升级 metadata codec 为 section 化协议。

## 验证计划

每个阶段至少执行：

- `cmake --build build_codex --config Release`
- `build_codex\Release\SchemaRegressionTests.exe`

阶段 1 到阶段 3 额外验证：

- 使用示例 `packager.yaml` 打包成功。
- 安装器能读取 metadata 并进入 GUI。
- 静默安装能完成或按预期拒绝旧版本覆盖。

阶段 4 到阶段 7 额外验证：

- 新旧 manifest builder 输出字段对比。
- payload offset 和 data package 读取测试。
- 组件选择安装测试。
- 升级清理和卸载清理执行级测试。

## 风险控制

- 每个阶段保持可编译、可测试、可回滚。
- 先修正确性，再做结构重构，最后做协议升级。
- adapter 过渡期只允许旧结构接收新结构投影，不允许继续在旧结构上扩展业务字段。
- 协议版本升级必须同步测试旧版本读取策略，不能隐式兼容。

已落地：

- 打包器主流程已改为构造 `PackageManifest` 并通过 section 化 codec 序列化 metadata。
- 安装器 metadata parser 已优先读取 section 化 `PackageManifest`，并投影到现有安装执行结构。
- 新增运行期 manifest validator，并接入扩展 metadata 校验入口。
- `desktopShortcutDefaultName` 与 `desktopShortcutLocalizedNames` 已补齐 round-trip。

剩余收尾：

- 安装器核心执行模块当前仍通过 adapter 使用 `ExtendedInstallationMetadata` 投影结构，尚未逐函数改为只接收 manifest 子结构。
- 旧 `BinaryMetadata` 读取链路已收敛：`metadata_binary_reader` 文件、构建项、legacy fallback、旧扩展序列化 API 和 `BinaryMetadata` 类型均已移除。
- `InstallationMetadata` 基础结构仍保留为旧结构投影和类型兼容支撑。
